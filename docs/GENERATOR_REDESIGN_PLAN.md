# 配置生成页整改计划

状态：暂停继续实施。用户明确要求组参数和规则添加在配置生成页就地完成，后续以 [配置生成简约与就地操作方案](GENERATOR_SIMPLICITY_PLAN.md) 为准。下文保留为历史记录。

最新调整（2026-11-25）：根据用户对按钮过多、展开内容过密的反馈，以下简化原则覆盖原计划中的默认展开要求：

- 生成页仅显示策略组列表和「DNS 覆写」开关，不显示规则 / 设置页签；模板使用一个下拉菜单。
- DNS、全局测速、端口和局域网参数在顶部总设置中保存为默认值；组测速覆写、容差和负载策略也在总设置配置。
- 策略组展开后只显示类型和成员编辑。规则从对应组打开独立窗口，支持查看完整规则条目、编辑保存及恢复来源。
- 节点编辑和二维码按钮保持直接可用，精简范围集中于分流区。
- 复制、删除、模板保存、导出、诊断和筛选与链式工具保留在菜单中。
- 使用 100 节点验证总设置保存、DNS 开关、组规则查看 / 编辑、配置保存、重启恢复、HTTP 输出和 Mihomo 校验；只做必要的功能操作，不再扩展布局巡检。

以下为原始整改计划记录，涉及布局巡检、三个入口和默认展开的描述均以以上最新约束为准。

## 目标与核对依据

优先整改配置生成主流程，尤其是右侧分流配置区的策略组、规则集和布局。成功标准是用户能在同一工作区完成「选节点 → 配置组成员 → 给组添加规则 → 检查生成结果 → 保存 / 更新配置」，不用在摘要列表与模板编辑界面之间寻找入口。

参考 [SubBoost 仓库](https://github.com/SubBoost/subboost)，本次核对版本为 `2832bcff66765d1f3843452b00b4a8bc4745b03d`。核对了仓库主界面截图、advanced-mode/root、proxy-groups-categories、proxy-groups-module-card、proxy-group-advanced-panel、规则编辑布局及目标投影实现。参考交互和信息结构，以 Rust / GPUI 独立实现。

SubBoost 截图中左侧是配置编辑、右侧是生成结果预览；SwiftSub 现有右侧是分流配置编辑区。整改应把编辑与结果的关系理顺，不机械交换左右位置。

## 已确认的问题

1. 主页面右侧依次堆叠筛选组、链式代理和模块摘要；深入编辑需要切换到 template_dialog 的另一套内容。日常编辑与模板保存耦合。
2. 策略组启停、类型、成员、规则来源和规则目标散落在不同入口，缺少一个可以直接操作的完整组卡片。
3. 规则库主要按来源展开，用户从某个组进入后仍需要理解来源和目标筛选，组拥有的规则不够直观。
4. 生成结果主要依赖 YAML，缺少从实际生成内容得到的组成员、链路、规则目标可视化。
5. 布局依赖较大的最小面板宽度与多层滚动，编辑状态还会更换整块面板，缺少不同窗口尺寸下的实际操作验收。
6. 已有测试证明了部分数据和生成正确性，尚不足以证明主界面的布局与操作体验合格。

## 一、先定布局和操作路径

宽窗口采用三块工作区：节点与来源、分流配置、生成预览。中等窗口默认节点与分流配置两栏，预览按需打开；较窄窗口允许收起节点区，保留完整编辑空间。

| 区域 | 内容与行为 |
| --- | --- |
| 顶部操作条 | 当前配置、模板选择、保存状态、保存新配置 / 更新原配置、预览开关 |
| 节点与来源 | 来源筛选、搜索、启停、排序、选中数量，保留现有节点编辑入口 |
| 分流配置 | 精简策略组列表、成员编辑、组规则入口及 DNS 覆写开关；基础与 DNS、测速参数统一放在总设置 |
| 生成预览 | 可视化 / YAML 切换，实际生成的节点、组、规则集统计；点击结果定位对应编辑内容 |

1440 像素及以上优先三栏；1280 像素优先两栏；1024 像素允许折叠节点并展开预览抽屉。具体宽度先通过线框和截图验证再定，不能把三个面板的最小宽度硬塞进窗口。

第一步交付：三种尺寸的布局线框、关键操作路径和界面状态清单。先验证布局，再铺功能。

## 二、统一编辑状态与生成数据

- 主工作区使用一份分流草稿，策略组卡片、规则库、模板保存和预览读取同一份状态；梳理当前 options 与 template_* 的同步关系，消除两个编辑界面各自维护内容的情况。
- 模板成为载入 / 保存当前草稿的操作，普通组编辑不需要进入模板界面。
- 建立节点、组、来源、规则绑定的稳定标识；显示名称变化不作为实体删除重建。
- 已保存配置的来源信息、停用状态和未知 YAML 字段继续保留；改名和规则移动明确更新引用。
- 明确草稿、有效生成结果和已保存配置三种状态。生成失败保留上次成功结果，显示当前问题；更新独立配置仍需明确保存。

交付：主工作区状态流转图和兼容已有模板 / 配置的迁移说明。

## 三、把策略组做成完整的可操作卡片

卡片收起时显示：组名称、类型、启停、成员数量、绑定规则集数量和编辑入口。展开后直接提供：

1. 名称、说明、类型选择：手动选择、自动测速、故障转移、负载均衡。
2. 成员选择：节点、其他组、筛选组、链式代理；搜索、来源 / 地区筛选、批量选择、成员排序。
3. 对应类型的参数：测速 URL、周期、容差、负载均衡策略等；不适用参数不混在一起。
4. 此组的规则：已绑定规则集、手写规则、添加规则、移动目标、停用 / 恢复。
5. 内置组恢复默认，自定义组复制 / 删除。删除或停用前展示被引用位置，支持选择替代目标。

核心组与服务组使用同样的组件；基础、媒体、AI、社交、游戏等分类允许独立折叠。分类数量、成员数量和规则集数量分别计算，不混用。

交付：核心组、自定义组和服务组都能在主页面完成编辑；不再依赖进入模板编辑才能改变成员。

## 四、重做规则集选择与归属

- 从组卡片点击「添加规则」时，默认绑定当前组。规则库提供来源分类、搜索、仅已添加、按目标筛选；当前目标始终可见。
- 同一视图显示内置规则、外部规则集和手写规则的类型、来源、目标、启停状态。
- 明确区分提供者定义与路由绑定。重复添加有明确反馈；切换目标执行规则移动，不误删其他组的规则。
- 全选 / 清空只作用于当前来源与筛选范围；离开规则库后，卡片里的数量和列表立即同步。
- 组内规则列表与全局执行顺序同时保留，跨组移动不暗中重排全部规则。兜底规则保持最后，冲突或覆盖提示能定位到具体规则。
- 对照 SubBoost 列出规则源、内置分流组和组参数的覆盖表，按日常使用优先补齐；不以目录条目数量代替功能验收。

验收例：给「AI 服务」添加两条规则集，将其中一条移到「自定义出口」，两组列表、计数、模板恢复与 YAML 目标必须一致。

## 五、连通筛选组、链式代理与结果预览

- 筛选组显示条件及实际匹配节点，可立即作为策略组成员选择；空匹配有明确提示。
- 链式代理显示完整顺序与节点状态，能作为分流目标；缺失、停用、重复和循环引用定位到具体链路。
- 可视化预览从实际生成结果构建，显示组类型、成员、默认顺序、链路及规则目标。不能只把编辑开关重新画一遍当作预览。
- 预览与 YAML 使用同一份成功生成结果；保存、导出和本地订阅正文保持一致。

## 六、验收方式

继续使用 100 节点，不扩大压力测试规模。最终验收重点是总设置、DNS 覆写及规则内容编辑的实际点击流程和输出一致性；下列多尺寸截图条目保留为早期记录，不作为本轮追加工作。

- 在 1440、1280、1024 像素宽度检查深色 / 浅色布局：操作不遮挡，关键按钮不被挤出，无页面横向溢出，展开组和规则库后仍能滚动到操作区域。
- 完成一条完整流程：导入节点 → 选择模板 → 新建组 → 选成员并排序 → 添加 / 移动规则 → 创建筛选组与链路 → 检查预览 → 保存 → 重启恢复 → 读取本地订阅。
- 分别验证四种策略组、改名、停用恢复、删除替换、来源批量选择及规则顺序。
- 核对主界面、模板恢复、实际 YAML、导出文件和 HTTP 输出一致；使用 Mihomo 校验代表性生成配置。
- 保留少量针对状态同步、目标归属、循环引用和恢复的回归测试。测试数量不作为界面完成标准。

## 执行顺序与完成标准

1. 布局线框与差距覆盖表。
2. 单一草稿状态和主工作区骨架。
3. 完整策略组卡片及规则库绑定。
4. 筛选组、链路与可视化预览联动。
5. 实际操作、三种窗口尺寸截图、重启与 Mihomo 验收。

本轮核心范围是配置生成页整改。备份提醒、历史搜索等附加升级暂不进入这一轮。最终交付必须包含可操作的新界面、实测截图和具体流程结果，不能只报告单元测试通过。
